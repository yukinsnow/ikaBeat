# ikaBeat 项目分析与重构记录

分析日期：2026-10-20。源代码基线：`3fa5b7e29ed9ff3c0a35a7859cf2bb99a9675228`。

## 结论

ikaBeat 的核心价值是简单的本地批量 BPM 检测，以及 ika 角色形成的视觉识别。值得保留的是这些产品特点和 Essentia 算法。需要替换的是依赖 AppKit 的桌面交互、仅能在 macOS ARM64 加载的动态库部署方式，以及界面与任务状态的耦合。

此交付实现了 Tauri 2 + React 19 + TypeScript + Vite + Essentia.js WebAssembly 的可运行重构版本。浏览器生产构建和真实 WASM 分析通过测试，四平台原生编译和打包也已在 GitHub Actions 通过；原生运行和实机验证尚未完成。最新产物及证据见 [构建结果](构建结果.md)。

## 现有代码的实际结构

| 文件 / 目录 | 职责 | 跨平台影响 |
| --- | --- | --- |
| `src/ikaBeatApp.swift` | SwiftUI 应用入口，窗口固定宽 400 | 需要响应式窗口和移动端入口 |
| `src/ContentView.swift` | UI、NSOpenPanel、文件过滤、拖入、结果状态 | 使用 AppKit，不能直接复用于 Windows / Android |
| `src/BPMDetector.swift` | DispatchQueue 异步任务、批量任务调度 | 可复用设计意图，需重写队列和生命周期 |
| `src/EssentiaWrapper.mm` | Objective-C++ 桥，MonoLoader 和 RhythmExtractor2013 | 绑定 Apple 平台与已有动态库 |
| `Frameworks/*.dylib` | Essentia、FFmpeg 及众多传递依赖 | 原仓库说明为 ARM64，不能直接用于其他平台 |
| `include/` | Essentia 头文件和算法源码等 | 并非现成的跨平台、可复现构建配置 |
| `Resource/` 和 xcassets | 横幅、角色图片、图标 | 可以直接保留 |

原有工作流：选择 / 拖入音频 → MonoLoader 以 44100 Hz 解码为单声道 → RhythmExtractor2013 → 界面显示 BPM。原 UI 接受 wav/aiff/flac/ogg/mp3。

## 具体问题

1. `EssentiaWrapper.mm` 成功路径未 delete `audioLoader` 和 `rhythmExtractor`；批量运行会积累分析对象。只有 loader.compute 被 try/catch 包围，factory.create 和 rhythmExtractor.compute 的异常未完整处理。
2. `BPMDetector.detectBPMForMultipleFiles` 使用输入下标 index+1 作为完成进度。任务乱序完成时进度可能倒退或提前到总数。
3. 批量方法先异步写入 resultsQueue，再 group.leave；group.notify 没有等待结果队列清空，最终回调可能读取未写完的 results。该方法与当前 UI 逐首调用的路径应区分，不能说它已导致所有 UI 分析错误。
4. UI 以数组下标接收结果，目前只追加时通常可用；一旦加入排序 / 删除就容易写错行。
5. 没有并发数量限制、取消、超时、用户可见的失败原因或完整任务模型。多首长音频可同时占用大量解码内存。
6. 固定宽度桌面布局、NSOpenPanel、Apple-only 运行时，决定了增加 iOS target 也不能直接实现四端。
7. 仓库包含 `Resource/icon/icon.iconset/Icon` 后带回车符的文件名，Windows 检出失败。新工程没有复制这个 Finder 元数据文件，保留有效图片内容。

## 技术选择和取舍

| 方案 | 适用性 | 本次决定 |
| --- | --- | --- |
| 继续 SwiftUI | 可以延续 Apple 平台体验；Windows / Android 仍需另建 UI | 不作为四端共同界面 |
| Flutter + C++ Essentia | 可统一 UI，并具有原生 DSP 路线；需要四端编译、链接、解码依赖和 FFI | 适合未来高性能原生引擎，但当前迁移工作量更高 |
| Tauri 2 + React + WASM Essentia | 四端框架入口、可共享 UI 和算法、原图直接复用、可先在浏览器验证 | 本次实现 |
| Electron | 桌面开发方便；手机端仍需额外方案 | 不选为统一平台壳 |

这里的“现代化”落实在类型约束、任务隔离、可取消生命周期、可复现依赖、生产构建测试和跨平台边界，而非为简单 BPM 工具引入服务端、数据库或大型 AI 模型。

Tauri 2 提供桌面和移动端框架支持，见[官方介绍](https://v2.tauri.app/start/)。Essentia.js 提供 WASM 算法，见[官方项目](https://mtg.github.io/essentia.js/)。这两点不等于本应用已经完成四端实机适配。

## 新架构

```mermaid
flowchart LR
  A[文件选择 / 桌面拖入] --> B[React 队列与稳定 ID]
  B --> C[系统 Web Audio 解码]
  C --> D[44.1 kHz 单声道]
  D --> E[独立 Worker / Essentia WASM]
  E --> F[BPM / 置信度 / 节拍]
  F --> G[界面 / 本地历史 / CSV]
```

队列一次只处理一首，避免分析并发堆积。每首结束或取消销毁 Worker，回收 WASM 内存。所有失败显示在对应条目；结果按 ID 更新；原始音频不存入历史。历史 JSON 解析失败会回退为空记录。

WASM 使用支持 Worker 的 UMD 构建。Essentia 包中的 `essentia-wasm.web.js` 是 window 专用版本，实际测试会出现 `document is not defined`，因此没有用于后台分析。上游 0.1.3 的 Emscripten / Embind 绑定还依赖动态 Function，CSP 因此需要 `unsafe-eval`，仅有 `wasm-unsafe-eval` 不够。已在生产环境测试这条真实约束；如果后续要求移除此权限，需要重新编译上游绑定或迁移原生引擎，不能只删配置。

暂时采用系统解码而非移植完整 FFmpeg，缩小依赖和打包范围，代价是各系统格式覆盖不同。若正式验收要求四端一致支持 FLAC / OGG / AIFF，下一阶段应实现统一解码适配层，并针对目标平台提供可重现构建和格式回归语料。

## 已执行验证

- TypeScript 严格类型检查和 Vite 生产构建。
- 单元测试：损坏历史恢复、非法历史过滤、CSV 转义及公式前缀处理、波形尾段。
- Chromium 生产构建端到端测试，启用与 Tauri 配置一致的 CSP。
- 实际运行 Essentia WASM 识别 120 / 140 BPM 合成脉冲，容差 ±3 BPM。
- 静音失败路径、串行队列、取消、恢复完成记录、CSV 下载。
- 390px 手机布局无横向溢出；桌面和手机截图已查看。
- npm audit 在当前锁文件下为 0 个已报告漏洞；这不代表完整安全审计。
